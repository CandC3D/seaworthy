# Secure execution, combat restrictions, and the macro / add-on boundary in World of Warcraft: Forever (client 1.60.1, interface 16001)

Research date: 2026-11-12. Evidence labels used throughout:

- **[Forever source]** = read directly from Blizzard's own interface code for the Forever client, `forever` branch of Gethe/wow-ui-source, head commit `4cd0ab7` titled "1.60.1 (70888)", committed 2026-11-10. This is the strongest evidence available: it is what the client actually ships. It shows only the Lua side; anything enforced in the C engine (macro conditionals, the 255-character truncation, macro chaining checks) is not visible there.
- **[Forever reported]** = stated by an add-on author, community tester or fan site about Forever, with date. Not Blizzard-confirmed.
- **[Carried over]** = documented for retail (Midnight 12.x) or Classic Era and not independently verified on Forever.

Status note: add-on listings still call Forever a beta, but two sources say it went live in early November 2026 (see first Gaps list). The API facts below come from build 70888 (10 Nov 2026) unless a different build is named.

Source file base path used in links: `https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/`

## 1. The protected-action model: hardware events, secure code paths, taint, the taint log, "action blocked"

### Takeaway
Forever uses the same secure-execution model as every client since 2.0: Blizzard code starts "secure", add-on and `/script` code is "tainted", and protected functions (casting, targeting, using items and similar) only succeed from a secure path, which in practice means a player click or key press on a secure button or a macro. The Forever source ships the full modern set of blocked/forbidden events, and Forever players and authors report the classic symptoms (silent failure, "blocked from an action only available to the Blizzard UI").

### Cited Findings
- **[Carried over, general model]** Execution starts secure and becomes tainted when it encounters taint, "an indicator that a function or object came from an untrusted source" (add-on or /script). At load, Blizzard code is secure and third-party add-on code is tainted. Taint persists until relog or interface reload. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Carried over]** How taint spreads: new values inherit the taint of the current execution path; "When code accesses tainted values, the resulting value will remain tainted and the execution path is also tainted"; "When code sets global values, the resulting value has the taint of the execution path"; function closures carry taint. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Carried over]** "A protected function is one that can only be successfully called from a secure execution state." `hooksecurefunc` lets add-ons post-hook a secure function without tainting it; `frame:HookScript` does the same for frame scripts. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Carried over, design intent]** The 2006 design statement behind the model: "addons and macros will no longer be capable of casting spells or targeting units" by themselves; Blizzard's Slouken clarified that add-ons can still cast spells with user interaction but cannot use logic to pick spells or targets. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Forever source]** The secure action handlers in the Forever client call the protected functions directly: `CastSpellByID`/`CastSpellByName` (spell), `SecureCmdUseItem`/`C_Item.EquipItemByName` (item), `TargetUnit`/`ClearTarget`/`SpellTargetUnit` (target), `FocusUnit`, `AssistUnit`, `RunMacro`/`C_Macro.RunMacroText` (macro). These run only when `SecureActionButton_OnClick` is reached from a real click or key binding. — [SecureTemplates.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)
- **[Forever source]** The template XML carries the comment that Blizzard's own usage supplies extra arguments and "for now AddOns won't be able to have isKeyPress or isSecureAction set" — i.e. add-on-created secure buttons cannot claim to be a genuine key press. — [SecureTemplates.xml, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.xml)
- **[Forever source]** The Forever API documentation defines four events for refused calls: `ADDON_ACTION_BLOCKED` and `ADDON_ACTION_FORBIDDEN` (payload: the tainting add-on name and the function name), and `MACRO_ACTION_BLOCKED` and `MACRO_ACTION_FORBIDDEN` (payload: function name). It also documents `C_RestrictedActions.CheckAllowProtectedFunctions(object, silent)`: "Returns true if the calling context has permissions to call protected functions on the supplied object", and `InCombatLockdown`. — [RestrictedActionsDocumentation.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsDocumentation.lua)
- **[Forever reported, 5 Nov 2026]** A player's `/ginvite` macro on Forever produced "A macro script has been blocked from an action only available to the Blizzard UI"; another poster said it "'ll start working after I /reload" (consistent with taint persisting until reload). No Blizzard reply in the thread. — [Blizzard forums, "WoW Forever Macros Broken"](https://us.forums.blizzard.com/en/wow/t/wow-forever-macros-broken/2401520)
- **[Forever reported, 28 Sep 2026]** An add-on calling `C_RecentAllies.TryRequestRecentAlliesData()` raised `ADDON_ACTION_FORBIDDEN`; `CopyToClipboard` is restricted to protected code. — [ForeverPlusPlus, docs/forever-api.md](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)
- **[Forever reported, build 69913, Sep 2026]** Some protected calls fail with no Lua error at all (`ChatFrame_OpenChat`, `C_SuperTrack.SetSuperTrackedUserWaypoint`, setting secure attributes on Blizzard frames); the only symptom is an interface-action counter in the AddOns panel that `/reload` does not reset. Wrapping the call in `pcall` hides nothing useful. — [WoW Forever Guides, addon pitfalls](https://wowforeverguides.com/addons/pitfalls)
- **[Forever reported, 15 Oct 2026]** Opening Blizzard windows from add-on code runs Blizzard's code tainted, and on Forever this now collides with secret values: `ToggleCharacter` called from a timer errored when Blizzard's code compared a secret number. The author's advice is to avoid `ToggleCharacter`, `OpenWorldMap`, `OpenAllBags`, `ShowUIPanel` from add-on code. — [ForeverPlusPlus, docs/forever-api.md](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)
- **[Carried over, with 12.x additions]** The taint log is the `taintLog` console variable; it writes to `World of Warcraft\Logs\taint.log` periodically and at logout. Levels: 0 off (default); 1 logs blocked actions and the taint events leading to them; 2 adds tainted reads/writes of globals; 3 upvalues and 4 table fields (added 12.0.0); 5 writes of secret values (added 12.0.1). — [Warcraft Wiki, CVar taintLog](https://warcraft.wiki.gg/wiki/CVar_taintLog)
- **[Forever, wiki changelog 8 Oct 2026, build 70291]** Hardware-event requirements were tightened in the Forever beta: `SendChatMessage` with the "EMOTE" type now requires a hardware event outside instances, matching "SAY" and "YELL". — [Warcraft Wiki, Patch 1.60.1/API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)
- **[Forever source]** A newer layer sits on top of taint: "forbidden aspects" on individual objects, e.g. `ScriptedInput` ("Restricts APIs that trigger synthetic input interactions on objects from Lua scripts"), `ScriptBindings` (no querying/replacing/hooking scripts), `ChangeParent`, `SetTexture`. — [ForbiddenAspectConstantsDocumentation.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ForbiddenAspectConstantsDocumentation.lua)

Evidence snippet (Forever source, the spell action). In plain English: when a secure button whose `type` is "spell" is clicked, read its `spell` attribute; if it is a number cast by ID, otherwise cast by name, at the unit resolved for the button.

```lua
SECURE_ACTIONS.spell = function (self, unit, button)
    local spell = SecureButton_GetModifiedAttribute(self, "spell", button);
    local spellID = tonumber(spell);
    if ( spellID ) then CastSpellByID(spellID, unit);
    elseif ( spell ) then CastSpellByName(spell, unit); end
end;
```

### Inferences
- "Action blocked by an add-on" in practice means: tainted code (or Blizzard code that became tainted by touching add-on data) reached a protected function. The call is refused, an `ADDON_ACTION_BLOCKED`/`FORBIDDEN` event names the add-on, and the fix is on the add-on side (stop touching Blizzard frames/globals), not the player side. `/reload` clears it temporarily.
- On Forever there are now two distinct failure families an author must separate: classic taint blocks (a protected function refused) and secret-value errors (Blizzard or add-on code doing arithmetic/comparison on a secret while tainted). The second is new relative to Classic Era and can be triggered just by an add-on opening a Blizzard panel.
- taintLog levels 3 to 5 exist in the 12.x engine that Forever shares, so they are very likely available on Forever; not directly confirmed.

### Gaps
- No Forever-specific list of protected functions was found; Blizzard has published no Forever-specific restricted-function list (per [wowforevertierlist, restrictions](https://wowforevertierlist.com/addons/restrictions), as of 8 Oct 2026).
- Movement: I found no source in this pass that states which movement functions are protected on Forever. The long-standing position that add-ons cannot move the character is general knowledge that I could not tie to a fetched source.
- An exact statement that casting/targeting/item use require a "hardware event" (as opposed to "secure execution path") was not found in a primary source; the sources describe the requirement as a secure path initiated by user interaction.
- Whether Forever is "in beta" or live: [SenseOS](https://senseos.gg/guides/wow-forever/macros/) says it went live 4 Nov 2026 23:00 UTC and [ForeverPlusPlus](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md) lists a "live client" 1.60.1.70755 dated 3 Nov 2026, while add-on pages (GodMacro, ZMacros) still describe it as beta on 6 to 12 Nov. Unresolved here; the other researcher covers product status.

## 2. Combat lockdown: what add-ons cannot change in combat, and the defer-until-combat-ends pattern

### Takeaway
Combat lockdown is unchanged in principle and confirmed present on Forever: in combat an add-on cannot create, edit or place macros, change bindings, change attributes on secure frames, or show/hide/move protected frames. Every Forever macro add-on that writes macros documents the same pattern: queue the change and apply it when combat ends.

### Cited Findings
- **[Carried over]** `InCombatLockdown()` "Returns true if the combat lockdown restrictions are active." Lockdown begins after `PLAYER_REGEN_DISABLED` fires and ends before `PLAYER_REGEN_ENABLED` fires. While active: "Programatic modification of macros or bindings is not allowed"; protected frames, their parents and frames anchored to them cannot be shown/hidden via Show/Hide, cannot have attributes changed, and cannot be moved by resetting points/anchors (user-initiated dragging is still allowed). — [Warcraft Wiki, API InCombatLockdown](https://warcraft.wiki.gg/wiki/API_InCombatLockdown)
- **[Carried over]** Protected frames must be created and configured out of combat; protection cannot be removed once applied; it propagates (temporarily) to parents and anchored frames. Add-ons should call `InCombatLockdown()` before creating or changing secure frames or attributes. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Forever source]** `InCombatLockdown` is documented in the Forever client's `C_RestrictedActions` system, and Blizzard's own secure-handler code enforces it: the SecureHandlers management API raises "Cannot use SecureHandlers API during combat", and frame handles are only handed out for a frame if it is protected or the player is not in combat. — [SecureHandlers.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureHandlers.lua); [RestrictedFrames.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedFrames.lua); [RestrictedActionsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsDocumentation.lua)
- **[Forever source]** `InsecureActionButtonTemplate` exists on Forever: "A template that can perform secure actions outside of combat"; its click script is literally `if not InCombatLockdown() then SecureActionButton_OnClick(self, button, down); end`. — [SecureTemplates.xml, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.xml)
- **[Carried over]** `CreateMacro` is marked restricted and cannot be called in combat; it became protected during combat in patch 2.0.1 (2006). — [Warcraft Wiki, API CreateMacro](https://warcraft.wiki.gg/wiki/API_CreateMacro)
- **[Forever reported, Nov 2026]** Modified (Interface 16001, v1.0.14, 11 Nov 2026): "WoW doesn't allow addons to create, edit or place macros during combat." Apply and Revert are queued until combat ends. — [CurseForge, Modified](https://www.curseforge.com/wow/addons/modified)
- **[Forever reported, 6 Nov 2026]** ZMacros (interface 16001): "Macros can't be created or placed in combat; ZMacros applies the change when combat ends." — [CurseForge, ZMacros](https://www.curseforge.com/wow/addons/zmacros)
- **[Forever reported, 3 Nov 2026]** Forever Macros (TomLabs): "A save in combat waits until the fight ends"; its Test button runs editor text once "(not in combat)". — [CurseForge, Forever Macros](https://www.curseforge.com/wow/addons/forever-macros)
- **[Forever reported, 25 Sep 2026]** Macro Wow Builder: macro creation is blocked in combat by Blizzard's API, which "isn't an addon limitation"; the window is opened out of combat. — [CurseForge, Macro Wow Builder](https://www.curseforge.com/wow/addons/macro-wow-builder)
- **[Forever reported, Oct 2026]** Macro Manager Forever: "protected macro operations may be unavailable during combat". MacroCraft advertises "combat lockdown safety checks". — [CurseForge, Macro Manager Forever](https://www.curseforge.com/wow/addons/macro-manager-forever); [CurseForge, MacroCraft](https://www.curseforge.com/wow/addons/macrocraft)
- **[Forever reported, 12 Nov 2026]** GodMacro: upkeep planning happens out of combat; "Combat keys cannot choose new recipients or swap consumables mid-fight." — [CurseForge, GodMacro](https://www.curseforge.com/wow/addons/godmacro)
- **[Forever reported]** Nameplate CVars cannot be set in combat on retail; the ForeverPlusPlus author assumes the same on Forever but marks it unverified. — [ForeverPlusPlus, docs/forever-api.md](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)
- **[Forever source]** Forever adds the Midnight "addon restriction" state machine alongside combat lockdown: restriction types `Combat`, `Encounter`, `ChallengeMode`, `PvPMatch`, `Map`, `Chat`, each `Inactive`/`Activating`/`Active`, announced by `ADDON_RESTRICTION_STATE_CHANGED`, which "will always be fired before a restriction becomes active, or after it is deactivated." — [RestrictedActionsConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsConstantsDocumentation.lua); [RestrictedActionsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsDocumentation.lua)

Standard deferral pattern (illustrative, not from a fetched source; it only uses functions confirmed above). In plain English: if the player is in combat, remember the job and run it when the "left combat" event fires; otherwise run it now.

```lua
local pending
local f = CreateFrame("Frame")
f:RegisterEvent("PLAYER_REGEN_ENABLED")
f:SetScript("OnEvent", function() if pending then pending(); pending = nil end end)
local function WhenOutOfCombat(job)
  if InCombatLockdown() then pending = job else job() end
end
```

### Inferences
- There are now two separate "combat" gates on Forever that a designer must keep apart: (a) combat lockdown, which blocks *changing* secure things and macros; and (b) the `Combat` add-on restriction, which makes combat *information* secret (section 4). `ADDON_RESTRICTION_STATE_CHANGED` gives add-ons a guaranteed last moment before secrecy starts, analogous to `PLAYER_REGEN_DISABLED` for lockdown.
- Anything a macro set needs (creating macros, placing them on bars, binding keys) must be finished before the pull. The unanimous queue-until-combat-ends behaviour across independent Forever add-ons is good evidence the restriction is enforced on Forever exactly as on other clients.

### Gaps
- No Forever-verified statement specifically about key-binding changes in combat was found (the wiki statement is general; the Forever key-binding documentation was not inspected for restriction flags).
- Whether `EditMacro` on an existing macro's *body only* is blocked in combat on Forever was not individually tested by any source found; add-on authors treat all create/edit/place operations as blocked.

## 3. Secure templates on Forever: SecureActionButtonTemplate, its attribute types, state drivers, secure handlers, the restricted environment, and the macrotext question

### Takeaway
All the secure templates exist in the Forever client source (build 70888): `SecureActionButtonTemplate`, `InsecureActionButtonTemplate`, `SecureUnitButtonTemplate`, secure handlers, state drivers, group and aura headers, and the restricted environment. The `macrotext` attribute is still read by the Forever secure button code and routed to `C_Macro.RunMacroText`, i.e. Forever has the post-11.0 retail design, not the Classic Era one: the wiki documents inline macrotext as capped at 255 characters and unable to `/click` buttons that would run other macros, and one Forever add-on author reports exactly that failure. Secure snippets were broken in the first beta build (69913) and fixed in build 70009 (23 Sep 2026).

### Cited Findings
- **[Forever source]** Templates defined: `SecureActionButtonTemplate` ("A button template for click-cast style action buttons"), `InsecureActionButtonTemplate`, `SecureUnitButtonTemplate`. — [SecureTemplates.xml, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.xml)
- **[Forever source]** `type` values with handlers in the Forever client: `menu`, `togglemenu`, `actionbar`, `action`, `actionrelease`, `pet`, `flyout`, `multispell`, `spell`, `toy`, `item`, `equipmentset`, `macro`, `cancelaura`, `leavevehicle`, `destroytotem`, `stop`, `target`, `focus`, `assist`, `maintank`, `mainassist`, `click`, `attribute`, `raidtarget`, `worldmarker`, `teleporthome`, `returnhome`, `visithouse`, `outfit`. (No `glyph` handler is present.) — [SecureTemplates.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)
- **[Forever source]** Unit-resolution attributes still present: `unit`, `checkselfcast`, `checkfocuscast`, `checkmouseovercast`, `allowVehicleTarget`, plus `helpbutton`/`harmbutton` virtual-button remapping; `useOnKeyDown` overrides the `ActionButtonUseKeyDown` CVar per button; `typerelease` and `pressAndHoldAction` exist for hold-and-release spells. — [SecureTemplates.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)
- **[Carried over, general reference]** Companion attributes per type (spell: `unit`,`spell`; item: `unit`,`item`; macro: `macro` or `macrotext`; target/focus/assist: `unit`; click: `clickbutton`; attribute: `attribute-frame`,`attribute-name`,`attribute-value`); modified-attribute naming is `modifier-name-button` with modifiers in the fixed order alt-, ctrl-, shift- and `*` wildcards; non-default clicks must be registered with `RegisterForClicks`. — [Warcraft Wiki, SecureActionButtonTemplate](https://warcraft.wiki.gg/wiki/SecureActionButtonTemplate)
- **[Forever source] macrotext is still wired up.** The `macro` handler: if a `macro` attribute exists it saves pending edits and calls `RunMacro(macro, button)`; otherwise it reads `macrotext` and calls `C_Macro.RunMacroText(text, button)`. — [SecureTemplates.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)
- **[Forever source]** `C_Macro.RunMacroText(text, button)` is documented in the Forever client with `HasRestrictions = true`; the client also has `C_Macro.SetMacroExecuteLineCallback`, which Blizzard's code captures once and then sets to nil ("explicitly only set this once per ui-instance"), so add-ons cannot install their own macro line executor. — [UIMacrosDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UIMacrosDocumentation.lua); [MacroExecutionManager.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/MacroExecutionManager.lua)
- **[Carried over, retail post-11.0]** The wiki's current description of the `macro` type: inline macrotext is limited to 255 characters and "cannot /click buttons that would execute other macros." — [Warcraft Wiki, SecureActionButtonTemplate](https://warcraft.wiki.gg/wiki/SecureActionButtonTemplate)
- **[Carried over, retail 11.0 history]** In the first 11.0.0 alpha the `macrotext` attribute "appears to have been removed" (issue opened 18 Apr 2024 by Meorawr; closed 3 Jul 2024); the developer intent relayed from that issue was that "one macro cannot '/click' a button that itself would execute another macro" and that macro chaining was being removed intentionally. Affected add-ons named: Clique, MacroToolkit, Total RP 3 Extended. `C_Macro.RunMacroText` and `RunMacroText` both appear in the 11.0.0 API change list. — [Blizzard forums, "/click macros 11.0.0"](https://us.forums.blizzard.com/en/wow/t/click-macros-1100/1910312); [Warcraft Wiki, Patch 11.0.0/API changes](https://warcraft.wiki.gg/wiki/Patch_11.0.0/API_changes)
- **[Forever reported, 3 Nov 2026]** Forever Macros (TomLabs, Interface 16001): add-ons on retail get past 255 characters with `/click` on hidden buttons, but "Forever does not run a button's macro text when a macro on the action bar clicks it." Recommended fix: "So split a long macro into two." — [CurseForge, Forever Macros](https://www.curseforge.com/wow/addons/forever-macros)
- **[Forever reported, Nov 2026]** Modified lists as a limit that "Macros cannot be placed inside a macro." — [CurseForge, Modified](https://www.curseforge.com/wow/addons/modified)
- **[Forever source]** The `click` action type and the `/click` slash command both survive, with a new guard: the target must not have access constraints and must not carry the `ScriptedInput` forbidden aspect before `:Click()` is called. — [SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua); [SlashCommands.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)
- **[Forever source] State drivers.** `RegisterStateDriver(frame, state, values)` is a wrapper for `RegisterAttributeDriver(frame, "state-"..state, values)`; the driver resolves its value with `SecureCmdOptionParse(values)`, i.e. the same macro-conditional strings a macro uses; `state-visibility` is special-cased to show/hide; updates are throttled (`STATE_DRIVER_UPDATE_THROTTLE = 0.2` seconds); `RegisterUnitWatch` exposes `state-unitexists`. — [SecureStateDriver.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureStateDriver.lua)
- **[Forever source] Secure handlers.** `SecureHandlerWrapScript`, `SecureHandlerUnwrapScript`, `SecureHandlerExecute`, `SecureHandlerSetFrameRef` exist; headers must be "explicitly protected"; the API refuses forbidden frames and refuses to run during combat. — [SecureHandlers.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureHandlers.lua)
- **[Forever source] Restricted environment.** Snippets see only a whitelist: basic math/string/table helpers; the "direct macro conditional" functions (`SecureCmdOptionParse`, `GetShapeshiftForm`, `IsStealthed`, `UnitExists`, `UnitIsDead`, `UnitIsGhost`, `UnitPlayerOrPetInParty`, `UnitPlayerOrPetInRaid`, the modifier-key tests, `GetMouseButtonClicked`, `IsMounted`, `IsSwimming`, `IsFlying`, `IsIndoors`, `IsOutdoors`, `CanExitVehicle`, and similar); action-bar queries (`GetActionBarPage`, `GetBonusBarOffset`, `HasAction`, a scrubbed `GetActionInfo`); and helpers `PlayerCanAttack`, `PlayerCanAssist`, `PlayerIsChanneling`, `PlayerPetSummary`, `PlayerInCombat`, `PlayerInGroup`, `UnitHasVehicleUI`, `RegisterStateDriver`, `RegisterAttributeDriver`, `RegisterUnitWatch`. There is no health, power, aura or cooldown function in the whitelist, and values crossing the boundary are passed through `scrub`. — [RestrictedEnvironment.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua)
- **[Forever source]** Frame handles inside snippets can `Show`, `Hide`, `SetPoint`, `SetAttribute`, `SetBindingClick`, `SetBinding`, `SetBindingSpell`, `SetBindingMacro`, `SetBindingItem`, `ClearBindings`, `SetParent`, etc. — this is the sanctioned way to change protected frames and override bindings during combat. — [RestrictedFrames.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedFrames.lua)
- **[Forever reported, 18 Sep 2026, build 69913]** In the first beta build secure snippets did not compile: `RestrictedExecution.lua` called `loadstring_untainted`, which the Forever client did not provide ("RestrictedExecution.lua:79: attempt to call a nil value"), breaking action-bar paging, secure group headers and click-casting (Clique named). — [WoW Forever Builds, 18 Sep 2026](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)
- **[Forever, wiki changelog]** Build 70009 (23 Sep 2026): "Fixed SavedVariables and RestrictedEnvironment not loading." — [Warcraft Wiki, Patch 1.60.1/API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)
- **[Forever reported]** Confirmation of the fix: secure snippets "work since" build 70009; `SecureHandlerBaseTemplate`'s `Execute(f, "return 42")` returned `true 42` in game. — [ForeverPlusPlus, docs/forever-api.md](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)
- **[Forever reported, Nov 2026]** GSE (sequence add-on) runs on Forever from version 3.3.38+, with the limits "GSE's own keybinds don't work in Forever" and the sequence must sit on an action bar button; a user's attempt to call a macro from within a sequence via `/click` did not work. — [WoW Lazy Macros forum thread, 3 to 9 Nov 2026](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)

Evidence snippet (Forever source, the macro action). In plain English: a secure button of type "macro" runs a saved macro if one is named; only if none is named does it run the inline `macrotext`, through the restricted `C_Macro.RunMacroText` function.

```lua
SECURE_ACTIONS.macro = function (self, unit, button)
    local macro = SecureButton_GetModifiedAttribute(self, "macro", button);
    if ( macro ) then
        securecallfunction(SaveMacro);
        RunMacro(macro, button);
    else
        local text = SecureButton_GetModifiedAttribute(self, "macrotext", button);
        if ( text ) then C_Macro.RunMacroText(text, button); end
    end
end;
```

### Inferences
- Answer to the critical question: yes, the retail 11.0+ macrotext regime is what Forever runs. The attribute exists and works for a button the player presses directly (key bound or clicked), but the pre-11.0 Classic Era tricks that depended on unlimited macrotext length and on macros clicking macro-running buttons are not available. This follows from (a) the Forever Lua being the 12.1.5-family code that calls `C_Macro.RunMacroText`, (b) the wiki's current limits for that code path, and (c) TomLabs' Forever-specific report. The 255-character cap on macrotext itself is engine-side and I did not find a Forever in-game test of it.
- Design consequence: a click-cast or key-bound secure button with `type="macro"` and short `macrotext` remains a valid add-on technique on Forever; "macro A clicks hidden button B which runs macro text C" does not.
- State drivers remain the only way for an add-on to react *securely* in combat, and they can only react to what macro conditionals can express (stance, modifier, target existence/hostility, combat, group, mounted and so on), never health, buffs or cooldowns, because the restricted environment exposes none of that.
- Early-beta articles saying click-casting and bar paging are "dead" on Forever are outdated since 23 Sep 2026.

### Gaps
- No in-game Forever test was found that measures the macrotext length cap or shows the exact error/behaviour when a macro `/click`s a macro-running button; the evidence is the wiki's retail description plus one add-on author's statement.
- I found no Forever-specific statement from Clique's or Macro Toolkit's authors on what they had to change. Macro Toolkit v2.3.53 (14 Oct 2026) ships a Forever TOC per [wowforeveraddons.com](https://wowforeveraddons.com/addons/macro-toolkit), but that page's "Works" label is based on release metadata, not in-game testing.
- Whether `SecureActionButton` with `type="spell"` honours rank suffixes on Forever was not tested by any source found.

## 4. Forever's information restrictions: is the Midnight "secret values" system present, what is secret and when, what an add-on can still do, and what breaks

### Takeaway
Yes. Blizzard stated on 15 Sep 2026 that Forever shares mainline's UI architecture and "The addon disarmament changes introduced in Midnight, including secrets, will also be active in Forever", and the Forever client source contains the whole secret-value machinery. In combat (anywhere, including open-world questing), health, most power, auras, cooldowns, threat and non-group unit identity reach add-on code as values it can hand to display widgets but cannot read, compare or calculate with; the combat log is closed to add-ons. Display add-ons survive by piping secrets straight into status bars, text and cooldown widgets; anything that makes decisions from combat data does not.

### Cited Findings

**Presence on Forever**
- **[Forever, Blizzard statement relayed by the wiki, 15 Sep 2026]** "WoW Forever shares Mainline WoW's UI architecture, including the vast majority of APIs available in 12.1.5." and "The addon disarmament changes introduced in Midnight, including secrets, will also be active in Forever." Forever ("Camelot") and Midnight ("Standard") are two game types in the mainline code family; the 12.1.0 AuraContainer/AuraButton changes are also in Forever. — [Warcraft Wiki, Patch 1.60.1/API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)
- **[Forever, secondary]** The statement originated in the WoW UI developer Discord and was reported by Wowhead on 16 Sep 2026 ("WoW: Forever Will Have Addon Changes from Midnight", by Squishei); in the 17 Sep 2026 live Q&A Blizzard said "Forever uses the modern client API." — [Wowhead news 382921](https://www.wowhead.com/news=382921/wow-forever-will-have-addon-changes-from-midnight); [wowclassicforever.info summary](https://wowclassicforever.info/news/addons-api/)
- **[Forever source]** The client defines `WOW_PROJECT_CAMELOT = 18` and sets `WOW_PROJECT_ID` to it. — [Camelot/ProjectConstants.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ProjectConstants/Camelot/ProjectConstants.lua)

**What a secret value is and what tainted code may do with it**
- **[Carried over, 12.0 definition]** Secret values "restrict the ability for addons to perform some operations on Lua values on tainted execution paths"; outside tainted execution they behave as ordinary values. Blizzard's stated goal is to limit "the ability for addons to perform complex logic and decision making based off combat information" while the changes are "not intended to prevent 'look and feel' customization of UI elements." — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values); [Warcraft Wiki, Patch 12.0.0/API changes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes)
- **[Carried over]** For tainted code the following raise an immediate Lua error on a secret: arithmetic; comparison and boolean tests (exception: non-boolean types can be truth-tested because the type is not secret, so nil is false and everything else true); the length operator; using it as a table key; indexing or assigning into it; calling it. Allowed: storing it in variables, upvalues or table fields; passing it to Lua functions; `type(secret)` returns the real type; strings and numbers may be concatenated and `string.format`/`string.join`/`string.concat` accept secrets (the result is itself secret). C functions must be explicitly marked as accepting secrets from tainted callers. — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)
- **[Carried over]** Test helpers: `issecretvalue(value)`, `canaccessvalue(value)`, `issecrettable(value)`, `canaccesstable(table)`. — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)
- **[Carried over]** Widget methods that accept secrets include `StatusBar:SetValue`, `FontString:SetText`, `EditBox:SetText`, `GameTooltip:SetText`, `Region:SetVertexColor`, `Cooldown:SetCooldown`, `TextureBase:SetTexCoord`. Doing so applies a "secret aspect" to the widget (Text, BarValue, Alpha, Cooldown and so on), after which the matching getter (e.g. `FontString:GetText()`) also returns secrets; aspects are cleared only with `SetToDefaults()`. Feeding a secret into an API with no linked aspect marks the whole object secret and makes its anchoring/position secret, which propagates to regions anchored to it. — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)
- **[Forever source]** Forever's secret-aspect list: Text, SecureText, Shown, Scale, Alpha, FrameLevel, ScrollRange, Cursor, VertexColor, Desaturation, TexCoords, BarValue, Cooldown, Rotation, MinimumWidth, Padding, CooldownStyle, TooltipTexture, ButtonState, ScrollOffset, RadialProgress, FrameStrata. — [SecretAspectConstantsDocumentation.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretAspectConstantsDocumentation.lua)
- **[Forever, wiki changelog 8 Oct 2026, build 70291]** The `FrameStrata` secret aspect was added in Forever beta 4; `GetFrameStrata` returns "a secret value" for frames with it. The same build fixed "a further issue allowing access to minimap rotation values during encounters". — [Warcraft Wiki, Patch 1.60.1/API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)

**Which APIs, under which conditions**
- **[Forever source]** Annotations in the Forever client documentation: `UnitHealth` is `SecretReturns = true` (no condition attached); `UnitHealthMax` is `SecretWhenUnitHealthMaxRestricted`; `UnitPower` is `SecretWhenUnitPowerRestricted`; `UnitName` is `SecretWhenUnitNameIdentityRestricted`; `UnitGUID` is `SecretWhenUnitIdentityRestricted`; `UnitThreatSituation` is `SecretWhenUnitThreatStateRestricted`; `UnitCastingInfo` is `SecretWhenUnitSpellCastRestricted`. — [UnitDocumentation.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua)
- **[Forever source]** `C_UnitAuras.GetAuraDataByIndex`, `GetBuffDataByIndex` and `GetPlayerAuraBySpellID` are `SecretWhenUnitAuraRestricted` (the last also `RequiresNonSecretAura`); `C_Spell.GetSpellCooldown` and `GetSpellCharges` are `SecretWhenCooldownsRestricted`; `C_Spell.IsSpellInRange` and `IsSpellUsable` carry no secret-return annotation. — [UnitAuraDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitAuraDocumentation.lua); [SpellDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellDocumentation.lua)
- **[Carried over, predicate meanings]** Aura and cooldown secrecy applies under combat, encounter, challenge-mode or PvP-match restrictions (per-spell "never"/"always" flags take priority for cooldowns); unit identity is secret when the unit is not player-controlled or in the party/raid; spell-cast info is secret when the unit is not the player or their pet; power/health-max secrecy applies to non-player-controlled units; chat lockdown and map restrictions apply in dungeons and raids. `UnitName` returns secrets for non-player, non-pet units in combat. — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)
- **[Forever reported, EverAuras author, page updated 10 Nov 2026]** "the moment you enter combat, anywhere (questing, dungeons or raids), aura and cooldown data become unreadable to addons." "A plain port of WeakAuras goes blind exactly when you need it." Debuffs on the player are matched by properties "since Blizzard hides which debuff it is in combat." Custom-code auras that compare secret values (the page's example is current mana) "cannot work in combat on Forever." — [CurseForge, EverAuras](https://www.curseforge.com/wow/addons/everauras)
- **[Forever reported, build 69913, 18 Sep 2026]** `/run local h = UnitHealth("player"); print(type(h), pcall(function() return h + 1 end))` printed `number false`; Grid2 threw "attempt to perform arithmetic on a secret number value (execution tainted by 'Grid2')". "Blizzard's own frames are unaffected." — [WoW Forever Builds, 18 Sep 2026](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)
- **[Forever reported, ForeverPlusPlus author, dated in-game observations]** In a solo open-world fight `UnitHealth`, `UnitHealthPercent` and `UnitHealthMissing` are secret for player and target, and the target's `UnitHealthMax` is secret; the player's `UnitHealthMax` and `UNIT_COMBAT` amounts stay readable. The player's own mana is secret even out of combat though its maximum is readable (5 Nov 2026). Friendly units' `UnitHealth` is secret out of combat on name-only nameplates (1 Oct 2026). `GetRaidTargetIndex` on a friendly player is secret (8 Nov 2026). `C_UnitAuras.GetAuraDataByIndex` threw "Auras cannot be accessed when secret while tainted" 149 times in one session (14 Oct 2026); aura secrecy is per spell via `C_Secrets.GetSpellAuraSecrecy(id)`. `Cooldown:SetCooldown` rejects secret numbers; use `C_Spell.GetSpellCooldownDuration` with `SetCooldownFromDurationObject`. Range checks (`C_Spell.IsSpellInRange`) stay readable in combat. - **[Forever reported]** Unit and creature names can be secret strings; printing one throws and can blank a frame, so check `issecretvalue` and fall back. `UnitCanAttack` is listed by one Forever site as returning a secret boolean (no build named). — [WoW Forever Guides, addon pitfalls](https://wowforeverguides.com/addons/pitfalls)
- **[Forever reported, GodMacro, 12 Nov 2026]** "Forever can hide health, mana, and other information"; GodMacro "reports unavailable checks rather than inventing values"; some health cues are "game-drawn only". It credits the WeakAuras-family forks (EverAuras, ForeverAuras, M33kAuras) for mapping what the Forever client lets add-ons see in combat. — [CurseForge, GodMacro](https://www.curseforge.com/wow/addons/godmacro)

**Combat log and communication**

**What an add-on can still legally do**
- **[Forever reported]** Pass the secret straight to setters (`SetMinMaxValues`, `SetValue`) without arithmetic. — [WoW Forever Guides, addon pitfalls](https://wowforeverguides.com/addons/pitfalls)
- **[Forever reported]** Use `SetFormattedText` with a secret for bar text; use `UnitHealthPercent(unit, true, curve)` with a step curve from `C_CurveUtil` to derive an alpha (the Midnight pattern; the `SetAlpha` step is unverified on Forever); gate reads behind `ShouldAurasBeSecret()` or `issecretvalue`; never read `GetPoint` on restricted regions ("Can't measure restricted regions"). — [ForeverPlusPlus, docs/forever-api.md](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)
- **[Forever reported]** EverAuras "hands those displays to the game engine instead, so they keep working"; the author lists as working in combat: "buffs, debuffs, DoT timer bars, cooldowns, range and resource checks", plus stacks, glows and party/raid buff tracking. — [CurseForge, EverAuras](https://www.curseforge.com/wow/addons/everauras)
- **[Carried over, Blizzard intent]** "Addons should not be able to automate combat decisions for the player"; add-ons can still adjust "the look of almost everything you see in the User Interface" but "will no longer be able to use that combat information to drive custom logic or make decisions for you." — [Blizzard, "How Midnight's Upcoming Game Changes Will Impact Combat Addons"](https://worldofwarcraft.blizzard.com/en-us/news/24244638/how-midnights-upcoming-game-changes-will-impact-combat-addons)
- **[Carried over]** Developer test CVars to force each restriction outside real combat: `addonCombatRestrictionsForced`, `addonEncounterRestrictionsForced`, `addonChallengeModeRestrictionsForced`, `addonPvPMatchRestrictionsForced`, `addonMapRestrictionsForced`, `addonChatRestrictionsForced` (not saved across restarts). — [Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)

**Which add-on categories break**
- **[Forever reported]** Raid-frame/healing add-ons that compute on health (Vuhdo, Grid2, Cell named); click-casting and bar paging were broken only in build 69913. — [WoW Forever Builds, 18 Sep 2026](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)

- **[Forever, secondary, as of 8 Oct 2026]** Cosmetic/structural add-ons (unit frames, bars, nameplate restyling; ElvUI has a Forever build) and out-of-combat add-ons (Questie, Auctionator, Baganator) are healthy; Details! has a Forever build dated 6 Oct 2026; DBM has a Forever core but no boss modules. — [wowforevertierlist, addon restrictions](https://wowforevertierlist.com/addons/restrictions)

### Inferences
- The add-on listing quoted in the brief ("the client hides buffs, debuffs and health from add-ons during combat") is accurate and is the Midnight secret-values system, confirmed three ways: Blizzard's statement, the client source, and multiple independent author reports.
- Forever is stricter than a casual reading of "in instances" suggests: several authors report secrecy in ordinary open-world combat, and a few values (own mana, friendly nameplate health) secret even out of combat. `UnitHealth` being annotated `SecretReturns = true` with no condition in the Forever documentation is consistent with that.
- Categories that cannot be rebuilt on Forever in their old form: rotation helpers/"next spell" advisers driven by add-on logic, threat meters, combat-log damage meters, health-threshold alerts, auto-marking, decurse/dispel assignment logic, smart heal-target selection. Categories that survive: anything that only *displays* (bars, text, cooldown swipes, auras drawn by the engine), anything out of combat, and anything that reads only player-owned casts and range.
- For a macro designer the important consequence is that no add-on on Forever can legitimately provide the "if my health is below X / if buff Y is missing, press this" decision layer in combat; GodMacro's phrasing ("reports unavailable checks rather than inventing values") shows authors hitting exactly this wall.

### Gaps
- Blizzard has published no Forever-specific list of which APIs are secret under which conditions; all Forever-specific detail is from the client documentation annotations and add-on authors' observations, which are per build and sometimes marked unverified by their own authors.
- The exact conditions under which `UnitHealth` is secret on Forever (always for tainted callers, or only under restrictions) are not settled by the sources: the annotation says unconditional, author reports describe combat plus some out-of-combat cases.
- I did not find upstream issue-tracker statements from Grid2, Clique, Details! or ElvUI maintainers about their Forever ports; the Grid2 error text comes via a third-party site.
- Whether registering `COMBAT_LOG_EVENT_UNFILTERED` errors or silently never fires on Forever is reported inconsistently.

## 5. The macro API available to add-ons: create/edit/delete/enumerate, slot counts, character limit, icons, long macros, running macros from code

### Takeaway
The macro API on Forever is the standard global set (`CreateMacro`, `EditMacro`, `DeleteMacro`, `GetNumMacros`, `GetMacroInfo`, `PickupMacro`), used by Blizzard's own Forever macro window. The Forever client constants are 120 account-wide and 30 per-character macro slots (not Classic Era's 18), with a 255-character body limit enforced in Blizzard's editor and documented by every Forever macro add-on. No Forever add-on found extends macro length, and the long-macro technique is reported not to work; running macro text from add-on code is a restricted function.

Evidence snippet (Forever source, how Blizzard's own window creates a macro). In plain English: create a macro with the typed name and chosen icon, with no body yet, as a character macro if the Character tab is selected.

```lua

index = CreateMacro(text, iconTexture, nil, isCharacterMacro) - macroFrame.macroBase;
```

### Inferences
- Slot budget for a macro set on Forever: 120 shared plus 30 per character. Add-ons or guides quoting 18 per character are using the Classic Era figure; Modified's default of 18 is its own conservative cap, not the client's.
- The 255-character limit is a hard limit on Forever with no working add-on bypass found. Combined with the macrotext/chaining restriction (section 3), "long macro" add-ons in the SuperMacro/Mega Macro tradition should be assumed not to work for combat use on Forever. A designer who needs more than 255 characters should split across two buttons/keys.
- Add-ons can fully manage the macro library out of combat (create, rename, re-icon, rewrite, delete, place on bars), which is why a whole crop of Forever macro builders exists; what they cannot do is execute those macros on the player's behalf in combat.
- The "?" icon behaviour (icon follows the first castable spell/item, or `#showtooltip`) is treated as present by Forever add-ons (MacroUI) and guides, consistent with the mainline engine.

### Gaps
- I found no explicit Forever test of what `CreateMacro` does with a body over 255 characters (silent truncation is documented for other clients only).
- I found no statement about Mega Macro or Super Duper Macro on Forever specifically (neither a Forever build nor a "does not work" notice). Macro Toolkit ships a Forever TOC (v2.3.53, 14 Oct 2026) per [wowforeveraddons.com](https://wowforeveraddons.com/addons/macro-toolkit), but whether its extended-macro feature functions on Forever is not documented there.
- `GetMacroIcons`/`GetMacroItemIcons` availability on Forever is implied by Macro Manager Forever's description, not confirmed from source in this pass.
- How Forever Macros' "Test" button executes text (which API) is not stated on its page.

## 6. What a macro can do that an add-on cannot, and the reverse; classic-era macro behaviours on Forever

### Takeaway
A macro is the only player-authored thing that can cast, target and use items in combat, but it is a fixed script evaluated on a key press with only the built-in conditionals: no health, buff, debuff or cooldown tests. An add-on can compute and display freely out of combat and display (not compute) in combat, but can never press the button. Forever's macro engine is the modern mainline one with Classic content: spell ranks are back and are addressed as `Spell(Rank N)`, mouseover/focus/targettarget/@cursor are present, `/castsequence` reset rules are unchanged in source, `/click` survives with a chaining restriction, and a handful of Forever-specific bugs are open.

### Cited Findings

**Macro-only powers and macro limits**
- **[Forever, secondary]** "A macro is a fixed sequence you wrote; the restrictions are on addon code reading combat state." Macros cannot choose an ability by cooldown, buff or enemy state, and cannot cast more than one (global-cooldown) ability per key press. — [wowforevertierlist, addon restrictions](https://wowforevertierlist.com/addons/restrictions); [wowforevertierlist, macros](https://wowforevertierlist.com/macros)
- **[Forever reported, 11 Oct 2026]** "Macros cannot check buffs or debuffs on a target", which the author attributes to the game's secure macro system rather than the add-on. — [CurseForge, Forever Macro-builder](https://www.curseforge.com/wow/addons/forever-macro-builder)
- **[Carried over]** Conditionals are meant to allow limited logic "without trivializing the game". The documented set: against the target — `exists`, `help`, `harm`, `dead`, `party`, `raid`; against the player — `combat`, `stealth`, `form`/`stance`, `mounted`, `swimming`, `indoors`/`outdoors`, `channeling`, `equipped`/`worn`, `group`, `pet`, `known`, `flying`, `flyable`, `resting`, `spec`; against the UI — `modifier`/`mod`, `button`/`btn`, `actionbar`/`bar`, `bonusbar`, `cursor`. Targeting keywords: `@unit` (alias `target=`), `@cursor` (ground under the cursor, added 7.1.0), `@none`. `no` prefix negates. — [Warcraft Wiki, Macro conditionals](https://warcraft.wiki.gg/wiki/Macro_conditionals)
- **[Forever source]** The functions Blizzard labels "direct macro conditional" functions on Forever cover stance/form, stealth, unit existence and death, group membership, modifier keys, mouse button, mounted, swimming, flying, indoors/outdoors, vehicle exit — no health, power, aura or cooldown query. — [RestrictedEnvironment.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua)
- **[Forever source]** `/cast` and `/use` on Forever: parse options with `SecureCmdOptionParse`, then `/cast` prefers a spell and falls back to an item, `/use` prefers an item and falls back to a spell. — [SlashCommands.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)
- **[Forever reported]** Confirmed working in a macro posted from the beta (2 Oct 2026): multiple `/cast` lines in one macro, `/startattack`, semicolon fallback chains, stance conditionals. Other conditionals are "standard WoW syntax and unverified on Forever" per that site. — [wowforevertierlist, macros](https://wowforevertierlist.com/macros)
- **[Forever reported, Nov 2026]** A melee ability failing with "Out of range" stops the remaining lines of the same macro, so melee lines should go last (GSE user testing on 1.60.1). — [WoW Lazy Macros forum thread](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)
- **[Forever reported, 25 Sep 2026]** Off-global-cooldown stacking is the accepted way to do more per press: Macro Wow Builder lets a macro add "up to four off-global-cooldown actions" (another spell, bag item, trinket, gear enchant, cancelling an own buff) plus `/stopcasting`, `/petattack`, `/startattack`. — [CurseForge, Macro Wow Builder](https://www.curseforge.com/wow/addons/macro-wow-builder)
- **[Forever, Blizzard beta notes via secondary, 8 Oct 2026]** Blizzard's 8 Oct 2026 beta notes "brought back swapping several weapons within the same global cooldown". — [SenseOS, WoW Forever macros](https://senseos.gg/guides/wow-forever/macros/)

**Cast sequences**
- **[Forever source]** `/castsequence` reset logic on Forever, read from the client: `reset=` accepts a number of seconds (timeout restarted on each press), `target` (resets on `PLAYER_TARGET_CHANGED`), `combat` (resets on `PLAYER_REGEN_ENABLED`, i.e. leaving combat), and `shift`/`ctrl`/`alt` (pressing with that modifier restarts); all sequences reset on player death; the sequence advances only on `UNIT_SPELLCAST_SUCCEEDED` for the pending cast and wraps after the last entry; items are allowed as entries. — [CastSequenceManager.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/CastSequenceManager.lua)
- **[Forever reported, 8 Nov 2026, live 1.60.1]** A user reports `/castsequence reset=target/combat …` "resets on every press, so Hunter's Mark gets recast every GCD and drains mana", whereas `reset=target` alone "works correctly"; tested both as a plain macro and inside GSE. — [WoW Lazy Macros forum thread](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)

**Spell ranks**
- **[Forever, secondary, citing Blizzard 1 Oct 2026 notes]** Forever restores spell ranks with a client setting to show all ranks or only the highest; low-rank casting carries penalties to spell damage/healing and proc chance (Blizzard's example: Rank 1 Frostbolt at level 60 has 0% chance to proc Frostbite). That site found no source explaining rank-casting syntax and declined to print rank macros. — [wowforevertierlist, macros](https://wowforevertierlist.com/macros)
- **[Forever reported]** Add-on authors do write ranks: Modified casts by name by default "which uses the highest known rank" and, with "Show all spell ranks" on, writes specific ranks such as `Spell(Rank 3)`; its rank discovery "relies on rank text such as 'Rank 3,'" with English names most reliable. Forever Macro-builder inserts spells with rank, e.g. `Healing Wave(Rank 5)`. GodMacro: "Automatic spell choices follow learned ranks, and exact-rank selection allows deliberate downranking." MacroCraft offers downranking and a Max Rank toggle. MacroLab Forever's spell picker can insert the spell name, the spell ID, or a `known:SPELLID` form. — [Modified](https://www.curseforge.com/wow/addons/modified); [Forever Macro-builder](https://www.curseforge.com/wow/addons/forever-macro-builder); [GodMacro](https://www.curseforge.com/wow/addons/godmacro); [MacroCraft](https://www.curseforge.com/wow/addons/macrocraft); [MacroLab Forever](https://www.curseforge.com/wow/addons/macrolab-forever)

**Mouseover, focus, target-of-target, at-cursor**
- **[Forever reported]** `[@mouseover]`/`[target=mouseover]` supported; `[target=targettarget]` supported; Blizzard's 15 Oct 2026 beta notes fixed a focus macro for Light's Vigil (implying focus macros are a supported case). — [SenseOS, WoW Forever macros](https://senseos.gg/guides/wow-forever/macros/)
- **[Forever reported]** Macro builders offering these targets on Forever: MacroCraft (Target, `@cursor`, `@mouseover`, `@player`, `@focus`); Macro Wow Builder (current target, mouseover, focus, self, pet, arena opponents 1 to 5, or a ground point for AoE/trap abilities); Forever Macro-builder (`@focus` and the Classic-relevant conditionals, with retail-only `[spec:]` and `[talent:]` "intentionally excluded"); Modified warns that Focus and Cursor targeting "depend on the game supporting `@focus` and `@cursor` for the spell." — [MacroCraft](https://www.curseforge.com/wow/addons/macrocraft); [Macro Wow Builder](https://www.curseforge.com/wow/addons/macro-wow-builder); [Forever Macro-builder](https://www.curseforge.com/wow/addons/forever-macro-builder); [Modified](https://www.curseforge.com/wow/addons/modified)
- **[Forever source]** Secure buttons support `checkfocuscast` (returns "focus") and `checkmouseovercast`, and there is a `focus` action type calling `FocusUnit`, so focus exists as a client feature. — [SecureTemplates.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)

**/click and /script**
- **[Forever source]** `/click ButtonName [mouseButton] [down]` is a secure command on Forever: it resolves the frame with `GetClickFrame`, requires it to be a Button without access constraints or the `ScriptedInput` forbidden aspect, then calls `button:Click(mouseButton, down)`. — [SlashCommands.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)
- **[Carried over / Forever reported]** A macro cannot `/click` a button that would execute another macro (wiki, current mainline behaviour); reported on Forever by the Forever Macros author (3 Nov 2026). — [Warcraft Wiki, SecureActionButtonTemplate](https://warcraft.wiki.gg/wiki/SecureActionButtonTemplate); [CurseForge, Forever Macros](https://www.curseforge.com/wow/addons/forever-macros)
- **[Forever source]** `/script` (and `/run`) on Forever: does nothing in kiosk mode, when the `UserScriptsDisabled` game rule is active, or when scripts are disallowed for a beta; on first use shows the `DANGEROUS_SCRIPTS_WARNING` confirmation unless dangerous scripts are already allowed; then calls `RunScript(msg)`. There is also a `MacrosDisabled` game rule that stops `/macro` from opening the macro window. — [SlashCommands.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)
- **[Carried over]** `/script` code is tainted like add-on code, so it cannot call protected functions. — [Warcraft Wiki, Secure Execution and Tainting](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)
- **[Forever reported, 6 Nov 2026]** A `/script SendChatMessage("…", "WHISPER", nil, GetUnitName("target"))` macro works on live Forever, while `/ginvite` macros fail (blocked-action error and Forever's two-part character names: "being unable to put both first and last name as 'target'"). — [Blizzard forums, "WoW Forever Macros Broken"](https://us.forums.blizzard.com/en/wow/t/wow-forever-macros-broken/2401520)
- **[Forever reported]** `ReloadUI()` worked from `/run`; GodMacro requires explicit confirmation before importing macros containing script or console commands. — [ForeverPlusPlus](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md); [CurseForge, GodMacro](https://www.curseforge.com/wow/addons/godmacro)

**Forever-specific differences and open bugs**
- **[Forever, secondary]** The 1.60.1 interface diff against retail 12.1.5 "contains no macro changes" beyond one gamepad fix. — [wowforevertierlist, macros](https://wowforevertierlist.com/macros)
- **[Forever reported, open bug since 24 Sep 2026]** `/cast !Shoot` toggles wand attack off on a second press, as if the `!` (do-not-toggle) prefix were absent; `/cast !Auto Shot` and `/cast !Stealth` work correctly (1 Oct). A related report (9 Oct): `/cast !Bear Form` while already in form disturbs `[form:1]` conditionals and blocks shapeshifting for about 3 seconds (powershift macros). Issue still open. — [ClassicWoWCommunity/forever-bugs issue #114](https://github.com/ClassicWoWCommunity/forever-bugs/issues/114)
- **[Forever reported, 6 Nov 2026]** One player reported macros using ctrl/shift modifiers with abilities left the client unable to log out and save the character (single unconfirmed report). — [Blizzard forums, "WoW Forever Macros Broken"](https://us.forums.blizzard.com/en/wow/t/wow-forever-macros-broken/2401520)
- **[Forever reported]** Spell names must match the Forever client exactly, "including new names in Forever" (e.g. 24 Sep 2026 notes renamed Mangle to Primal Bite); ZMacros builds macros from spell IDs so names follow the client language, and offers `/zm check` because "Forever is in beta: if a patch changes a spell". — [SenseOS, WoW Forever macros](https://senseos.gg/guides/wow-forever/macros/); [CurseForge, ZMacros](https://www.curseforge.com/wow/addons/zmacros)
- **[Forever reported]** Old global helper functions used in Classic `/script` macros are gone: `GetSpellInfo`, `GetItemInfo`, `UnitAura`, `GetContainerItemInfo`, `IsAddOnLoaded`, the talent globals; use `C_Spell.*`, `C_Item.*`, `C_UnitAuras.*`, `C_Container.*`, `C_AddOns.*`. — [ForeverPlusPlus](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md); [WoW Forever Guides, pitfalls](https://wowforeverguides.com/addons/pitfalls)

**What an add-on can do that a macro cannot**
- **[Forever reported]** Persisting data, building UI, scanning the spellbook and bags, validating and explaining macro text, versioning and undo (Forever Macros keeps the last 30 deleted macros; MacroLab Forever saves a version on every save), export/import (Macro Wow Builder: "the text is parsed field by field, never run as Lua"), placing macros on bar slots and binding keys out of combat (ZMacros: pick the key by pressing it and the macro goes on the button that key triggers; "You can bind a key directly to a macro without using a bar button"). — [Forever Macros](https://www.curseforge.com/wow/addons/forever-macros); [MacroLab Forever](https://www.curseforge.com/wow/addons/macrolab-forever); [Macro Wow Builder](https://www.curseforge.com/wow/addons/macro-wow-builder); [ZMacros](https://www.curseforge.com/wow/addons/zmacros)
- **[Forever source]** Add-ons, unlike macros, can react during combat through secure state drivers and secure handler snippets, but only to macro-conditional state. — [SecureStateDriver.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureStateDriver.lua)

### Inferences
- The division of labour on Forever: macros own the *action* (cast/target/use, one GCD action per press, conditionals limited to stance, modifier, target type, combat state and the like); add-ons own *authoring, placement and display*. Neither can make health/buff/cooldown-based choices in combat: macros never could, and add-ons lost the information via secret values.
- Classic Era macro habits that need adjusting on Forever: (a) `/script` snippets using removed globals must be rewritten to `C_*` APIs; (b) `/script` logic that reads health/auras for in-combat decisions will now hit secret values; (c) macro chaining via `/click` is gone; (d) per-character slots are 30 rather than 18; (e) `@cursor` and `[known:]` are available because the engine is modern; (f) rank syntax `Name(Rank N)` is what add-on authors emit, and by-name casts use the highest known rank.
- The `/castsequence reset=target/combat` misbehaviour is a single user report that contradicts what the Lua source would do (source resets on combat only when leaving combat); treat it as an unconfirmed bug or user error, but prefer a single reset condition when designing.
- "No conditional on health, buffs or cooldowns" is supported indirectly (conditional list, restricted-environment whitelist, add-on author statement) rather than by a single Blizzard sentence.

### Gaps
- No Blizzard statement or Forever-specific test confirms the exact rank syntax (`Spell(Rank N)`); it is inferred from three independent add-ons emitting that form.
- `@cursor` is offered by Forever add-ons but Modified hedges on game support; no explicit in-game confirmation on Forever was found. `[known:]` on Forever is implied by MacroLab Forever's picker only.
- The macro-conditional parser (`SecureCmdOptionParse`) is engine-side; I could not verify the full Forever conditional list from source. The wiki list carries no per-flavour flags and is marked potentially out of date.
- Whether the `!` prefix bug (issue #114) is fixed in build 70888 is unknown; the issue was still open when fetched.
- A guide claim surfaced in search results that "multi-spell macros on the global cooldown don't work in one click anymore" could not be found on the page it was attributed to; discarded.

## 7. Macro-building add-ons published for Forever: techniques, documented limits, and what they reveal about the API

### Takeaway
At least a dozen macro add-ons target Interface 16001. They all generate ordinary macro text and store it through the standard macro API; none executes actions itself, none bypasses the 255-character limit, and those that write macros queue changes until combat ends. Their shared limits are the clearest practical map of the Forever API boundary.

### Cited Findings
- **ZMacros** (Zael9898, v1.0.3, 6 Nov 2026, MIT, interface 16001): library of "367 class macros + 18 general ones, built from the full Forever spellbook"; macros built from spell IDs so names follow client language; the user picks a key by pressing it and the macro is placed on the button that key triggers (works with Blizzard bars and bar add-ons); can bind a key directly to a macro; moves a modifier option if it collides with the chosen key; "Macros can't be created or placed in combat; ZMacros applies the change when combat ends"; sharing macros with other players is blocked by the game during boss encounters and Mythic+; `/zm check` for spell changes during beta. — [CurseForge, ZMacros](https://www.curseforge.com/wow/addons/zmacros)
- **Macro Wow Builder** (Megathium, v1.2.0, 25 Sep 2026): point-and-click generator; Simple mode (one ability, one target, reaction filter, fallback target) and Advanced mode (up to four behaviours on one key: plain, Shift, Ctrl, Alt); non-spell slots (bag items, trinkets, on-use enchants); up to four off-GCD extra actions; never overwrites existing macros; export/import as text "parsed field by field, never run as Lua"; creation blocked in combat by Blizzard's API. — [CurseForge, Macro Wow Builder](https://www.curseforge.com/wow/addons/macro-wow-builder)
- **Forever Macro Creator** (ASadSin, v1.0.0, 24 Sep 2026, MIT, interface 16001, English clients only): side panel beside Blizzard's Macro window with 260+ templates for the nine classes; detects learned abilities; "INSERT INTO BLIZZARD" writes code into the currently selected Blizzard macro (a macro must be created or selected first); 255-character counter; notes that add-ons cannot write to the OS clipboard. — [CurseForge, Forever Macro Creator](https://www.curseforge.com/wow/addons/forever-macro-creator)
- **Macro Manager Forever** (Darkspore, v0.8.74, 18 Oct 2026, interface 16001): create/edit/delete General and Character macros, drag to bars; editor enforces 255; plain-language explanation of commands and conditionals; icon browser over 27,714 stock icons; 246-entry command finder; "designed around the Forever client's APIs" and may not work on Retail or Classic; "protected macro operations may be unavailable during combat". — [CurseForge, Macro Manager Forever](https://www.curseforge.com/wow/addons/macro-manager-forever)
- **MacroLab Forever** (Dkaywow, v1.4.3, 8 Oct 2026): in-game editor with autocomplete, line-by-line validator (unknown commands checked against a curated list plus a dynamic scan of slash-command globals, which also catches add-on commands), Dry-Run simulation of each line "at the current moment", per-save versioning, "Space Save" compression, spell picker inserting name, ID or `known:SPELLID`, 255 counter. — [CurseForge, MacroLab Forever](https://www.curseforge.com/wow/addons/macrolab-forever)
- **Modified: Macro Manager** (mager1794, v1.0.14, 11 Nov 2026, Interface 16001; also lists 120007): visual designer per action-bar button; it "writes the macro, puts it on the button and keeps it up to date"; one character macro per managed button named `Mod_<slot>`; generates `/cast` or `/castsequence` with `[mod:shift]`, `[@mouseover,help,nodead]`, `[@player]`, `exists`, `reset=` options; items written as `item:<id>` with `/use`; documented limits: 255 characters (Apply disabled over the limit), default 18 character slots or the game's maximum, no create/edit/place in combat (queued), "Macros cannot be placed inside a macro", items only by drag-and-drop, Revert cannot restore mounts/pets/flyouts/equipment sets, rank discovery depends on "Rank N" text. — [CurseForge, Modified](https://www.curseforge.com/wow/addons/modified)

### Inferences
- Common technique: read the live spellbook/bags, assemble standard macro text, store with `CreateMacro`/`EditMacro` (or inject into Blizzard's open macro editor), optionally place on a bar slot and/or bind a key, all out of combat. None of the pages names the API calls, but the behaviours (General vs Character tab storage, 255 cap, drag to bars, combat deferral) match the calls seen in Blizzard's own Forever macro UI source.
- Two integration styles exist: (1) own the macro slot (Modified's `Mod_<slot>`, ZMacros' placed-and-bound macros, Macro Wow Builder's never-overwrite creation) and (2) assist Blizzard's editor (Forever Macro Creator's insert-into-selected-macro). Style 2 avoids slot management and combat-queue logic entirely.
- What the documented limits reveal about the Forever API: macro writes and bar placement are combat-locked; 255 characters is firm; macros cannot nest or chain; add-ons cannot write the clipboard; add-on-to-add-on sharing is shut off in encounters; the spell and rank data add-ons depend on shifts between builds; and combat-state checks (health, mana) may simply be unavailable. Every one of these matches the source-level findings in sections 2 to 5.
- The repeated "the player presses the key / does not cast automatically" disclaimers show authors positioning themselves on the permitted side of Blizzard's automation line (section 8).
- Download counts are small (tens to low thousands) and most projects are four to eight weeks old, so none is yet a de facto standard; behaviour claims are self-reported.

### Gaps
- None of the add-on pages documents its implementation at API level; source repositories were not inspected, so "uses CreateMacro/EditMacro" is an inference from behaviour.
- How ZMacros binds "a key directly to a macro" (which binding API, and whether it uses a secure button) is not stated.
- GodMacro's own "bar" presumably uses secure action buttons, but its page does not say so.
- No Forever macro add-on found claims to support macros longer than 255 characters; absence of such an add-on is not proof that it is impossible.

## 8. Blizzard's enforcement posture: permitted add-on or macro versus prohibited automation

### Takeaway
The line is unchanged in principle and tightened in mechanism: in-game macros and add-ons that work through the provided API are a supported feature, with the player supplying each key press; software or hardware that multiplies, repeats or broadcasts inputs, or plays unattended, is treated as cheating. For Forever specifically, Blizzard's stated position is that add-on restrictions follow retail's and that add-ons must not make combat decisions for the player; no Forever-specific macro policy statement was found.

### Cited Findings
- **[Blizzard, Midnight statement that Blizzard says applies to Forever]** "Addons should not be able to automate combat decisions for the player." Add-ons "will no longer be able to use that combat information to drive custom logic or make decisions for you." — [Blizzard, "How Midnight's Upcoming Game Changes Will Impact Combat Addons"](https://worldofwarcraft.blizzard.com/en-us/news/24244638/how-midnights-upcoming-game-changes-will-impact-combat-addons)
- **[Forever, secondary reports of developer interviews, Sep 2026]** Kotaku interview (Mike Nuthals): the in-combat add-on disarmament carries over and add-ons won't perform the calculations that automate marking or calling out for players, though "specifics weren't confirmed". Massively OP: "Addon restrictions will be similar to retail's", naming automatic communication and automatic marking. Game Informer (via Wowhead): add-ons are supported and kept in line with retail, but Blizzard doesn't want them to take too much control of the game. — [wowclassicforever.info, with links to Kotaku, Massively OP and Wowhead](https://wowclassicforever.info/news/addons-api/)
- **[Forever]** Blizzard has published no Forever-specific restricted-function list and no forum blue post on add-on restrictions; players asked on 16 Sep and 3 Oct 2026 without a reply (as of 8 Oct 2026). — [wowforevertierlist, addon restrictions](https://wowforevertierlist.com/addons/restrictions)
- **[Carried over, standing policy]** UI Add-On Development Policy (released 20 Mar 2009, enforced from 19 May 2009): add-ons must be free of charge; "The programming code of an add-on must in no way be hidden or obfuscated"; no in-game advertising or donation requests; must follow the Terms of Use and EULA; "Blizzard Entertainment reserves the right to disable any add-on functionality within World of Warcraft." — [Blizzard forums, UI Add-On Development Policy](https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534)
- **[Carried over, standing policy]** Input broadcasting: Blizzard announced that use of input-broadcasting software that mirrors keystrokes to multiple WoW clients "will soon be considered an actionable offense", with warnings escalating to account actions "which can include suspension and, if necessary, permanent closure"; "We strongly advise you to cease using this type of software immediately". The stated reason was its growing use for botting and automated play. — [Blizzard, Policy Update for Input Broadcasting Software](https://worldofwarcraft.blizzard.com/en-us/news/23558957/policy-update-for-input-broadcasting-software)
- **[Carried over, seen only as a search-result summary]** A May 2021 update extended the prohibition to all software and hardware mechanisms that mirror commands to multiple accounts or automate or streamline multi-boxing; multiboxing itself is not a Terms of Use violation. — [Blizzard forums, "Policy Update for Input Broadcasting - May 2021"](https://us.forums.blizzard.com/en/wow/t/956611/1)
- **[Carried over, community reading, not official text]** The working rule on the forums is "one key press = one action": in-game macros are a game feature; external tools that add delays, repeats or multiple inputs per press are treated as automation; holding a key to auto-repeat is a disputed grey area with at least one reported ban. Forum posters cite the Terms of Use clause against using third-party programs to automate any facet of the game. — [Blizzard EU forums, "Keyboard Mashing through Keyboard Software"](https://eu.forums.blizzard.com/en/wow/t/keyboard-mashing-through-keyboard-software/367927); [Blizzard US forums, hardware macros and RSI thread](https://us.forums.blizzard.com/en/wow/t/i-am-looking-for-an-official-interpretation-of-the-tos-on-the-usage-of-hardware-macros-to-avoid-rsi/1415005)
- **[Forever, wiki changelog]** Enforcement through the API continued during the Forever beta: 8 Oct 2026 (build 70291) — trial accounts can no longer send add-on messages, `EMOTE` chat needs a hardware event outside instances, a leak of minimap rotation values during encounters was closed; 16 Oct 2026 (build 70425) — GUID parts obfuscated "to prevent layer comparison". — [Warcraft Wiki, Patch 1.60.1/API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)
- **[Forever source]** The client has game rules that can switch off user scripts (`UserScriptsDisabled`) and macros (`MacrosDisabled`) entirely, and `/script` requires a one-time "dangerous scripts" confirmation. — [SlashCommands.lua, forever branch](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)
- **[Forever reported]** Add-on authors position themselves explicitly: GodMacro — the player presses the key, the add-on is "not unattended automation"; MacroUI — "generates macros but does not cast spells automatically". — [CurseForge, GodMacro](https://www.curseforge.com/wow/addons/godmacro); [CurseForge, MacroUI](https://www.curseforge.com/wow/addons/macroui)
- **[Forever, secondary]** A fan site cites Blizzard Support articles "Are Macros Allowed in World of Warcraft?" and "Problems Setting Up Macros in World of Warcraft" (read 8 Oct 2026) as its basis for saying macros are permitted. — [wowforevertierlist, macros](https://wowforevertierlist.com/macros)

### Inferences
- Blizzard enforces the add-on side mainly by engineering (protected functions, combat lockdown, secret values, hardware-event requirements, forbidden aspects), and reserves account action for things outside the client: input broadcasters, key-press multipliers, timed-sequence tools, bots. A macro set built entirely inside the in-game macro system, and an add-on that only uses the documented API, sit clearly on the permitted side.
- Sequence add-ons such as GSE remain in the tolerated in-client category on Forever (they run, one press advances one step), but pairing them with external key-repeat software is what crosses the line; that pairing is the main practical enforcement risk for macro-heavy players.
- Because Blizzard patches leaks during the beta (minimap rotation, GUID layer comparison), any add-on technique that recovers hidden combat information through a side channel should be expected to be closed and should not be designed around.

### Gaps
- The text of Blizzard Support's "Are Macros Allowed in World of Warcraft?" article was not retrieved; I could only confirm it is cited by a fan site. No official sentence stating "one key press, one action" was found; that formulation is community paraphrase.
- No Forever-specific statement from Blizzard on macros, key-press multiplication or sequence add-ons was found.
- The current End User License Agreement / Terms of Use wording on automation was not fetched in this pass (quoted only via forum posts); the policy researcher should supply the exact clause.
- The input-broadcasting announcement page shows "November 3rd" without a year; the year is not confirmed from the page itself.
