# Macros Act, Add-ons Display, Neither Decides

World of Warcraft: Forever runs the retail Mainline client (patch 1.60.1, interface 16001, live build 70888 on 10 November 2026), so its macros and add-ons obey Midnight's rules, not Classic Era's. A macro is a fixed script of at most two hundred and fifty-five characters, run on one key press, that may cast, target and use items in combat but can branch only on a small built-in set of conditions: stance, modifier key, target kind, combat state and the like, never health, buffs or cooldowns. An add-on is a folder of Lua 5.1 files with a manifest declaring interface 16001; it can build interface, store data, and write, place and bind macros out of combat, but it can never cast, and in combat the values it would need to decide anything (health, auras, cooldowns, threat) reach it as "secret values" that it may hand to display widgets but may not read, compare or compute with. The one route by which add-on code acts during combat, secure handlers and state drivers, can test only the conditions a macro can test, so that condition set is the ceiling for both. Building and publishing is conventional: develop in the `_forever_` install's add-on folder, test with the built-in debugging commands and in real combat, tag a git release, and let the BigWigs packager upload to CurseForge and Wago, both of which carry a Forever flavour. Three points correct the earlier macro report: a character has thirty macro slots, not eighteen; the `/castsequence` advance-on-success rule is now confirmed in Forever's own source; and secrecy is wider than "in combat". Lua-side facts below are read from Blizzard's exported Forever source; engine-side behaviour, and anything no one has yet tested in game one week after launch, is marked as inferred.

## Forever is retail's client, and half its rules can be read

Forever launched on 4 November 2026 ([Blizzard News](https://news.blizzard.com/en-us/article/24315820/world-of-warcraft-forever-now-live)). Its interface code is public: the `forever` branch of the exported client UI source reads **1.60.1.70888**, committed 10 November 2026, and sits beside separate branches for retail (12.1.5), the retail test realm (12.1.7) and the Classic clients ([wow-ui-source, forever branch](https://github.com/Gethe/wow-ui-source/tree/forever)). Blizzard's statement of 15 September 2026, relayed by Warcraft Wiki from a developer Discord post that this research could not open, is that Forever "shares Mainline WoW's UI architecture, including the vast majority of APIs available in 12.1.5," and that Midnight's "addon disarmament changes … including secrets, will also be active in Forever" ([Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). The wiki documents the API as a delta from retail: one hundred and seventy-six global functions added and ten removed between 12.1.5 and 1.60.1, as of the diff dated 2 October 2026 ([Warcraft Wiki, 1.60.1 API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)).

Two identifiers matter to an author. The manifest game type is `camelot`, the internal codename, with `forever` accepted as an alias since beta build 70291 (7 October 2026); Blizzard said the codename would be renamed before launch, but its own files in build 70888 still use `camelot` throughout ([Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes); [wow-ui-source, forever branch](https://github.com/Gethe/wow-ui-source/tree/forever)). In Lua, the client sets the global `WOW_PROJECT_ID` to `WOW_PROJECT_CAMELOT`, whose value is **18**; this is verified in the Forever source ([ProjectConstants.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ProjectConstants/Camelot/ProjectConstants.lua)). The interface number is a poor discriminator: 16001 is below 20000 although the client is a 12.x-family build, so code that reads a low number as "old API" misclassifies Forever. Add-on maintainers test the project ID, and guard the comparison because two undefined globals compare equal on clients that define neither ([BetterBags maintainer notes](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)).

The evidence in this report falls into three classes, named where they apply. **Verified** means read from the Forever branch at build 70888, which is what the client ships. **Reported** means stated by an add-on author or player about Forever, with a date. **Carried over** means documented for retail 12.x and inferred to hold through the shared client. The uncertainty that applies throughout is this: the exported source shows only the Lua side. The macro-condition parser, the truncation of long macro bodies and the refusal of macro chaining live in the C engine and cannot be read; no one in this research ran code in a Forever client; and Blizzard has published no Forever-specific list of protected functions, of secret APIs, or of macro policy ([wowforevertierlist, restrictions](https://wowforevertierlist.com/addons/restrictions)). Reported behaviour is per build and the game is eight days old.

## A macro is 255 characters of fixed script in one of 150 slots

### The command set is retail's, with spell ranks restored

The slash commands that act (`/cast`, `/use`, `/castsequence`, `/target`, `/click`, `/startattack`, `/stopmacro`, `/cancelaura`, `/equip`) are verified in the Forever source. They are registered into a private table that add-on code cannot reach, under a comment stating that insecure code may not register secure slash commands. `/cast` and `/use` each pass their bracketed conditions to the engine's option parser; `/cast` then prefers a spell and falls back to an item, and `/use` does the reverse ([SlashCommands.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)).

Player reports extend what the earlier report could confirm. A macro posted from the beta on 2 October 2026 used several `/cast` lines, `/startattack`, semicolon fallbacks and stance conditions ([wowforevertierlist, macros](https://wowforevertierlist.com/macros)). A launch-build guide lists mouseover, target-of-target and focus targeting as supported ([SenseOS](https://senseos.gg/guides/wow-forever/macros/)), and the secure button code in the Forever source carries focus-cast and mouseover-cast attributes and a `focus` action ([SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)). Blizzard's notes of 8 October 2026 restored swapping several weapons within one global cooldown, including by macro ([Blizzard forums, development notes](https://us.forums.blizzard.com/en/wow/t/2360696)). Spell ranks are addressed as the spell name followed by the rank in parentheses, and a bare name casts the highest known rank; players posted working downrank macros on 8 November, and three independent Forever add-ons emit the same form ([Blizzard forums, downranking](https://us.forums.blizzard.com/en/wow/t/downranking-spells/2406434); [Modified](https://www.curseforge.com/wow/addons/modified); [Forever Macro-builder](https://www.curseforge.com/wow/addons/forever-macro-builder)). Blizzard has documented no rank syntax. The remainder of the condition list, including `@cursor` and `known`, is carried over from the retail parser ([Warcraft Wiki, macro conditionals](https://warcraft.wiki.gg/wiki/Macro_conditionals)).

### The limits, and how firmly each is known

| Limit | Value | Basis, as of 12 November 2026 |
|---|---|---|
| Body length | 255 characters; comment lines count | Verified in Blizzard's Forever macro editor, whose edit box is declared with 255 letters. Truncation of longer bodies written by code is carried over. |
| Name length | 16 characters | Carried over from the general API page. |
| Account-wide slots | 120 | Verified in Forever's constants. |
| Per-character slots | 30, indexed 121 to 150 | Verified in Forever's constants and macro window. |
| Abilities per press | One on the global cooldown; actions off the global cooldown may accompany it | Reported on Forever; carried over. |
| Conditions | Stance, stealth, modifier, mouse button, target existence and hostility, death, combat, group, mounted, swimming, indoors, channeling, equipped, pet, known; no health, aura or cooldown | List carried over; the absence is corroborated by Forever source. |
| Chaining | A macro cannot click a button that would run another macro | Carried over from retail 11.0; reported on Forever 3 November. |

A macro body holds at most two hundred and fifty-five characters ([Blizzard_MacroUI.xml](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_MacroUI/Blizzard_MacroUI.xml)), and an account holds one hundred and twenty shared macros plus thirty per character, one hundred and fifty in reach of any one character ([MacroConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/MacroConstantsDocumentation.lua); [Blizzard_MacroUI.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_MacroUI/Blizzard_MacroUI.lua)). A macro's name is limited to sixteen characters by the current interface, a figure carried over from the general API page ([Warcraft Wiki, CreateMacro](https://warcraft.wiki.gg/wiki/API_CreateMacro)). The length limit has no working bypass. The older long-macro add-ons advertised bodies of up to one thousand and twenty-three characters (1,023) ([Mega Macro](https://www.curseforge.com/wow/addons/mega-macro)), and on retail such tools pass the limit by having a short macro click a hidden button that carries longer text; the author of Forever Macros reports on 3 November 2026 that "Forever does not run a button's macro text when a macro on the action bar clicks it," and advises splitting a long macro across two keys ([Forever Macros](https://www.curseforge.com/wow/addons/forever-macros)). No Forever add-on found claims to extend macro length.

The absence of a health, buff or cooldown condition rests on more than the wiki list. The Forever source labels a set of functions "direct macro conditional" functions; the set covers stance, stealth, unit existence and death, group membership, modifier keys, mouse button, mounted, swimming, flying, indoors and vehicle exit, and holds no health, power, aura or cooldown query ([RestrictedEnvironment.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua)).

`/script` and `/run` survive, gated. The Forever source shows they do nothing in kiosk mode or when a game rule named `UserScriptsDisabled` is active, show a one-time warning on first use, and then run the text ([SlashCommands.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)). The script runs tainted, like add-on code, so it cannot cast and it meets the same secret values. Classic-era script macros also fail for a plainer reason: the old global helpers (`GetSpellInfo`, `UnitAura`, `GetItemInfo`, `GetContainerItemInfo`) are gone and must be rewritten against the `C_Spell`, `C_UnitAuras`, `C_Item` and `C_Container` namespaces ([ForeverPlusPlus API notes](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)).

### Three corrections to the earlier macro report

**Per-character slots number thirty.** The earlier report left the count open between eighteen and thirty and called it undocumented for Forever. The Forever constants settle it at thirty; eighteen is the figure on the general wiki page and the Classic Era habit ([MacroConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/MacroConstantsDocumentation.lua); [Warcraft Wiki, CreateMacro](https://warcraft.wiki.gg/wiki/API_CreateMacro)).

**The cast-sequence rule is confirmed in source.** The earlier report marked as unverified that a `/castsequence` step advances only when the spell casts. Forever's cast-sequence manager advances only on the spell-cast-succeeded event for the pending cast, wraps after the last entry, and resets on a timeout restarted by each press, on target change, on leaving combat, on a named modifier, and on death ([CastSequenceManager.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/CastSequenceManager.lua)). That is read from code, not tested in game. One user reported on 8 November that a combined `reset=target/combat` resets on every press while `reset=target` alone works ([WoW Lazy Macros thread](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)); the report contradicts the source and is unconfirmed, but a single reset condition avoids the question.

**Secrecy is not confined to combat.** The earlier report described aura data as hidden "during combat." Author reports show secrecy in ordinary open-world fights, and a few values secret outside combat; the detail is in the next section.

Four defects are reported and unanswered by Blizzard. `/cast !Shoot` toggles the wand off on a second press as if the no-toggle prefix were absent, open since 24 September 2026, with its status in build 70888 unknown ([forever-bugs issue 114](https://github.com/ClassicWoWCommunity/forever-bugs/issues/114)). A `/ginvite` macro produced the blocked-action message on 5 November, and Forever's two-part character names defeat name-based targeting ([Blizzard forums, macros broken](https://us.forums.blizzard.com/en/wow/t/wow-forever-macros-broken/2401520)). A melee ability that fails as out of range stops the remaining lines of its macro, so melee lines belong last ([WoW Lazy Macros thread](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)). Spell names must match the Forever client exactly, including names Forever changed ([SenseOS](https://senseos.gg/guides/wow-forever/macros/)).

## Lockdown blocks changes; secrets block reading

Two separate mechanisms govern add-on code, and they answer different questions. Secure execution and combat lockdown decide what code may *do*. Secret values decide what code may *know*. Classic Era had only the first.

### Casting is reserved to secure code that a key press starts

Blizzard's code starts secure. Add-on code and `/script` text are tainted, and taint spreads to every value and execution path that touches it until the interface reloads. A protected function succeeds only from a secure path ([Warcraft Wiki, secure execution](https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting)). The Forever source shows where the protected calls live: the handlers behind a secure action button call the cast, item-use, target, focus, assist and run-macro functions directly, and those handlers run only when the button's click routine is reached from a real click or key binding ([SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)). The spell handler, as shipped:

```lua
SECURE_ACTIONS.spell = function (self, unit, button)
    local spell = SecureButton_GetModifiedAttribute(self, "spell", button);
    local spellID = tonumber(spell);
    if ( spellID ) then CastSpellByID(spellID, unit);
    elseif ( spell ) then CastSpellByName(spell, unit); end
end;
```

In words: when a secure button of type "spell" is clicked, read its `spell` attribute and cast it, by number or by name, at the unit the button resolves. An add-on may create such a button and set its attributes; only the player's press fires it.

A refused call raises one of four documented events, two for add-ons and two for macros, naming the function and, for add-ons, the offending add-on ([RestrictedActionsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsDocumentation.lua)). Forever adds a failure that Classic Era authors will not expect: opening a Blizzard panel from add-on code runs Blizzard's own code tainted, and that code can then fail on a secret comparison. One author reported exactly this on 15 October 2026 when calling the character-window toggle from a timer ([ForeverPlusPlus API notes](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)). The diagnostic is the `taintLog` console variable, which writes blocked actions and their taint history to a log file; its higher levels, added in retail 12.0, are carried over and unconfirmed on Forever ([Warcraft Wiki, taintLog](https://warcraft.wiki.gg/wiki/CVar_taintLog)).

### Combat lockdown freezes macros, bindings and secure frames

Lockdown starts after the enter-combat event and ends before the leave-combat event. While it holds, code cannot create or edit macros or change bindings, and cannot show, hide, move or re-attribute protected frames ([Warcraft Wiki, InCombatLockdown](https://warcraft.wiki.gg/wiki/API_InCombatLockdown)). That description is carried over, but Forever enforces it visibly: the secure-handler management code in the Forever source raises an error when used during combat ([SecureHandlers.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureHandlers.lua)), and every Forever macro add-on that writes macros documents the same behaviour. ZMacros, for one: "Macros can't be created or placed in combat; ZMacros applies the change when combat ends" ([ZMacros](https://www.curseforge.com/wow/addons/zmacros)). The standard pattern follows: test `InCombatLockdown()`; if it is true, hold the job and run it when the leave-combat event fires. No source tested binding changes in combat on Forever individually.

### Secure buttons, state drivers and snippets are the sanctioned in-combat path

All the secure templates are verified present in build 70888. `SecureActionButtonTemplate` carries thirty action types, among them spell, item, macro, target, focus, assist, click, pet, cancel-aura and stop ([SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)). A button of type "macro" runs a saved macro if one is named and otherwise runs inline text from its `macrotext` attribute through a restricted function. This is the retail regime introduced in 11.0, not Classic Era's: inline text is capped at two hundred and fifty-five characters and cannot click a button that would run another macro ([Warcraft Wiki, SecureActionButtonTemplate](https://warcraft.wiki.gg/wiki/SecureActionButtonTemplate)). A key-bound or click-cast secure button with short inline macro text remains a valid technique; a chain of macro, hidden button and longer macro does not.

For reacting during combat, an add-on has state drivers and secure handler snippets. A state driver hands the engine a macro-condition string; the engine evaluates it, at most once every two tenths of a second (0.2 s), and writes the result to an attribute on a protected frame ([SecureStateDriver.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureStateDriver.lua)). A snippet is a string of Lua that Blizzard's code compiles and runs in a restricted environment when the attribute changes. Inside that environment a snippet may show, hide, move and re-attribute protected frames and rebind keys, all during combat ([RestrictedFrames.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedFrames.lua)). What it may *see* is a whitelist: basic math, string and table helpers, the macro-condition functions, and action-bar queries. No health, power, aura or cooldown function is on the list, and values crossing the boundary are scrubbed ([RestrictedEnvironment.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua)). This is how action-bar paging by stance and click-casting work. The mechanism failed to compile in the first beta build, 69913, and was fixed in build 70009 on 23 September 2026 ([Warcraft Wiki, 1.60.1 API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)); articles from that first week calling click-casting dead on Forever are stale.

### A secret value can be shown but not inspected

A secret value is an ordinary Lua number, string or boolean that tainted code may hold but not examine. Arithmetic, comparison, boolean tests, the length operator, use as a table key, indexing and calling all raise an immediate error. Storing it, passing it to functions, asking its type, and concatenating or formatting it (the result is itself secret) are allowed ([Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)). A tester on the first beta build ran this line:

```lua
/run local h = UnitHealth("player"); print(type(h), pcall(function() return h + 1 end))
```

It asks for the player's health, then prints the value's type and whether adding one to it succeeds. The output was `number false`: the type is visible, the arithmetic is refused ([WoW Forever Builds, 18 September 2026](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)).

The way out is the display widget. Status bars, font strings, tooltips, colour setters and cooldown swipes accept secrets and draw them; the widget then acquires a "secret aspect," after which its matching getter returns secrets too. Forever's source lists twenty-two such aspects, including one for frame strata added in beta build 70291 ([SecretAspectConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretAspectConstantsDocumentation.lua); [Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). An add-on can therefore draw a correct health bar without ever knowing the health. Helper functions (`issecretvalue`, `canaccessvalue`) let code test before it touches a value, and the `C_Secrets` namespace reports which classes of data are currently secret, per spell where needed ([SecretPredicateAPIDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretPredicateAPIDocumentation.lua)). Retail documentation is not a safe guide to which setters accept secrets on Forever: the wiki lists the plain cooldown setter as accepting them, while a Forever author reports that it rejects secret numbers and that a duration object must be used instead ([ForeverPlusPlus API notes](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)).

### What is secret, and when

Secrecy is driven by a state machine with six restriction types (combat, encounter, challenge mode, PvP match, map, chat), each inactive, activating or active, announced by an event that always fires before a restriction takes hold ([RestrictedActionsConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsConstantsDocumentation.lua)). The Forever API documentation annotates each function. Unit health is marked as returning secrets with no condition attached. Maximum health, power, unit name, unit identifier, threat and cast information are secret under named conditions. Aura lookups and spell cooldowns are secret when auras or cooldowns are restricted. Spell range and spell usability carry no secret annotation ([UnitDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua); [UnitAuraDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitAuraDocumentation.lua); [SpellDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellDocumentation.lua)).

Reports from the live client fill in the conditions, and they are stricter than "in instances." The author of EverAuras, a WeakAuras successor, wrote on 10 November 2026: "the moment you enter combat, anywhere (questing, dungeons or raids), aura and cooldown data become unreadable to addons" ([EverAuras](https://www.curseforge.com/wow/addons/everauras)). Another author's dated observations: in a solo open-world fight, current health is secret for player and target while the player's maximum health stays readable; the player's own mana is secret even out of combat (5 November); friendly health on name-only nameplates is secret out of combat (1 October); range checks stay readable in combat ([ForeverPlusPlus API notes](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)). The exact conditions for health are unsettled: the annotation says unconditional, the reports describe combat plus some cases outside it.

The combat log is closed to add-ons. Retail 12.0 made registering for the combat-log events an error and removed most of the functions that read them ([Warcraft Wiki, 12.0.0 API changes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes)); on Forever one author reports the event never fires and names the built-in damage-meter API and the per-unit combat event as substitutes, while sources disagree on whether registering for it raises an error or fails silently ([ForeverPlusPlus API notes](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md); [WoW Forever Guides](https://wowforeverguides.com/addons/pitfalls)). The same build that ships these restrictions ships Blizzard's replacements: the Damage Meter, Cooldown Manager and aura container all load for the Forever game type, though retail's Encounter Timeline and Encounter Warnings are marked for the retail game type only in build 70888 ([wow-ui-source, forever branch](https://github.com/Gethe/wow-ui-source/tree/forever)).

The consequence by category is an inference from the above, not a Blizzard list. Add-ons that only draw (unit frames, bars, cooldown swipes, auras rendered by the engine) survive; EverAuras claims working in-combat buff, debuff, cooldown, range and resource displays by handing them to the engine. Add-ons that compute on combat state (rotation advisers, threat meters, log-parsing damage meters, health-threshold alerts, automatic marking) cannot be rebuilt in their old form. Grid2, unported, failed on the first beta build with "attempt to perform arithmetic on a secret number value" ([WoW Forever Builds, 18 September 2026](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)).

## An add-on is a folder, a manifest and event-driven Lua 5.1

### The folder and the manifest

An add-on lives at `World of Warcraft\_forever_\Interface\AddOns\<Name>\`. The folder name rests on CurseForge's migration guide of 25 October 2026 and on add-on authors' notes, which agree; no Blizzard page states it, and the macOS path is unverified ([CurseForge blog](https://blog.curseforge.com/wow-forever-migrate-addons-beta-to-live/)). The Retail and Classic folders are separate installs, and add-ons placed there do not appear in Forever. Inside the folder sits a manifest, a `.toc` file whose name must equal the folder's name or the client will not detect the add-on ([Warcraft Wiki, add-on tutorial](https://warcraft.wiki.gg/wiki/Create_a_WoW_AddOn_in_15_Minutes)). A complete manifest from a Forever-only template:

```
## Interface: 16001
## Title: Forever Addon Template
## Notes: Starting point for a WoW Forever addon
## Author: Tautellini
## Version: @project-version@
## SavedVariables: ForeverAddonTemplateDB

ForeverAddonTemplate.lua
```

The first line declares the client build the add-on targets; a mismatch flags it out of date. The next four are the name, tooltip, author and version shown in the in-game add-on list, the version being a placeholder that the release packager replaces with the git tag. `SavedVariables` names one global table the client will write to disk at logout and restore at login. The last line lists the code files, which run in the order given ([ForeverAddonTemplate.toc](https://github.com/Tautellini/TautelliniAddons/blob/HEAD/templates/ForeverAddonTemplate/ForeverAddonTemplate.toc); [Warcraft Wiki, TOC format](https://warcraft.wiki.gg/wiki/TOC_format)).

An add-on that also targets retail can list several interface numbers on the first line, separated by commas, or ship per-client manifests distinguished by filename suffix. The client looks first for a game-specific suffix (`_Forever` or `_Camelot`), then the family suffix (`_Mainline`), then the plain file ([Warcraft Wiki, TOC format](https://warcraft.wiki.gg/wiki/TOC_format)). A Forever-only add-on needs none of this.

### The runtime

The language is Blizzard's modified Lua 5.1, with no operating-system or file library ([Warcraft Wiki, Lua functions](https://warcraft.wiki.gg/wiki/Lua_functions)). Each file receives two arguments, the add-on's name and a private table shared by all its files; that table replaces globals as the place for shared state. The 1.60.1 diff adds an `import` function, renamed from `require` on 8 October 2026, but whether third-party code may use it is not established ([Warcraft Wiki, 1.60.1 API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)). Globals remain necessary for three things only: the saved-variables table, slash-command registrations, and any deliberate public interface.

Everything is event-driven. The add-on creates an invisible frame, registers event names on it, and supplies one handler. The sequence at login is fixed: an add-on-loaded event fires once per add-on, after its files and saved variables have loaded, and is the earliest safe point to read saved data; a login event fires once, when most world information is available; an entering-world event fires on every loading screen. Saved variables are written at logout and are lost on a crash ([Warcraft Wiki, add-on loading](https://warcraft.wiki.gg/wiki/AddOn_loading_process)). A slash command is registered by assigning a global whose name begins `SLASH_` and adding a handler to a global command table ([Warcraft Wiki, add-on tutorial](https://warcraft.wiki.gg/wiki/Create_a_WoW_AddOn_in_15_Minutes)). An options page is built with the `Settings` API, which a Forever-only add-on uses to bind a checkbox to a key of its saved table and list the page under Options ([ForeverLootSparkles.lua](https://github.com/svengabr/ForeverLootSparkles/blob/HEAD/ForeverLootSparkles.lua)).

The API to call is retail's `C_` namespace world, and the reference is the Forever branch itself: the folder `Blizzard_APIDocumentationGenerated` holds machine-readable signatures with the secret and restriction annotations, the in-game `/api` command browses the same data, and the wiki's 1.60.1 page gives the delta ([wow-ui-source, forever branch](https://github.com/Gethe/wow-ui-source/tree/forever); [Warcraft Wiki, API](https://warcraft.wiki.gg/wiki/World_of_Warcraft_API)). Where a retail wiki page and the Forever branch disagree, the branch governs. The API is retail-shaped but the content is not: Forever has nine character bank tabs and no account bank although the bag enumeration still declares account entries, and its unit frames were reskinned on 16 October 2026 with child frames moved, so code must check that a frame exists before anchoring to it ([Tautellini Forever guide](https://github.com/Tautellini/TautelliniAddons/blob/HEAD/docs/forever-addon-development.md); [Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)).

Frameworks are optional. Ace3, the long-standing library suite, lists 16001 in its own manifest ([Ace3.toc](https://github.com/WoWUIDev/Ace3/blob/master/Ace3.toc)), and BetterBags and Questie embed it in their Forever builds. The small Forever-only add-ons inspected (ForeverLootSparkles, DoesItDie, WorldLight) use none: a private table, one event frame and the `Settings` API suffice ([ForeverLootSparkles.toc](https://github.com/svengabr/ForeverLootSparkles/blob/HEAD/ForeverLootSparkles.toc); [DoesItDie.toc](https://github.com/swirllyman/DoesItDie/blob/HEAD/DoesItDie/DoesItDie.toc)). Not every library is clean; BetterBags' maintainer records that a bundled drop-down library mis-detects Forever and falls into none of its client modes ([BetterBags maintainer notes](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)).

### Testing

The in-game tools are retail's, and their Blizzard source ships on the Forever branch, though no source confirmed each one's behaviour in the Forever client. `/reload` re-runs all add-on code. `/console scriptErrors 1` shows Lua errors. `/dump` prints an expression, `/tinspect` opens a table inspector, `/etrace` logs events as they fire, and `/fstack` names the frames under the cursor ([Warcraft Wiki, add-on tutorial](https://warcraft.wiki.gg/wiki/Create_a_WoW_AddOn_in_15_Minutes)). Sources conflict on manifest changes: the wiki tutorial says a reload can replace a restart, while a Forever author says new files and manifest edits need a full client restart ([Tautellini Forever guide](https://github.com/Tautellini/TautelliniAddons/blob/HEAD/docs/forever-addon-development.md)). Restarting after adding files is the safe reading.

Secrets change what a test proves. Code that does arithmetic on health runs without fault in a city and fails at the first pull, so the same author's rule is to test in the open world, in a dungeon and in a boss encounter before release ([Tautellini Forever guide](https://github.com/Tautellini/TautelliniAddons/blob/HEAD/docs/forever-addon-development.md)). The retail wiki lists console variables that force each of the six restriction types on outside real combat; they are carried over and unconfirmed on Forever ([Warcraft Wiki, Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)). One open-source add-on ships a companion probe whose sole job is to report which combat data add-ons can read on the current build ([DoesItDie](https://github.com/swirllyman/DoesItDie)).

Outside the game, Forever authors keep the source in git and link it into the add-on folder with a directory junction. They lint with `luacheck` set to the Lua 5.1 standard and an explicit whitelist of permitted globals, so an accidental global fails the build ([ForeverLootSparkles .luacheckrc](https://github.com/svengabr/ForeverLootSparkles/blob/HEAD/.luacheckrc)). The common editor support, Ketho's WoW API extension for the Lua language server, does not advertise a Forever annotation set; its retail annotations are the nearest fit and will offer some functions Forever lacks ([vscode-wow-api](https://github.com/Ketho/vscode-wow-api)). Nothing runs add-on code outside the client; the repositories that test offline carry hand-written stubs of the game API.

### Publishing

The release pipeline is the one retail authors use. A GitHub Actions workflow triggers on a pushed version tag and runs the BigWigs packager, which zips the add-on, substitutes the version, creates a GitHub release and uploads to the hosts named by project identifiers in the manifest. The packager's script maps any interface number of the form 16xxx to the Forever game type ([packager release.sh](https://github.com/BigWigsMods/packager/blob/master/release.sh)). **CurseForge and Wago both carry a distinct Forever flavour at version 1.60.1**; a file not tagged with it is invisible in the Forever filter ([Wago game data API](https://addons.wago.io/api/data/game); [ThiccUI on CurseForge](https://www.curseforge.com/wow/addons/thiccui)). WoWInterface lists no Forever game type, and the packager skips it ([WoWInterface compatibility API](https://api.wowinterface.com/addons/compatible.json)). One trap is verified in the packager's source as of 12 November 2026: it scans manifests suffixed `_Camelot` but not `_Forever`, although the client and Wago accept both. A plain, unsuffixed manifest avoids it.

Blizzard's standing add-on policy, dating from 2009, applies to anything published: add-ons must be free, their code must not be hidden or obfuscated, and they may not solicit donations in game ([Blizzard forums, UI Add-On Development Policy](https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534)).

## The boundary runs between the key press and the computation

| Capability | Macro | Add-on, out of combat | Add-on, in combat |
|---|---|---|---|
| Cast, target, use an item | Yes, on the player's press | Only by configuring a secure button the player presses | The same button works; its configuration is frozen |
| Branch on stance, modifier, target kind, combat state | Yes | Yes | Yes, through state drivers and secure snippets only |
| Branch on health, buffs, debuffs, cooldowns | No | May read what is not secret and rewrite macros or reconfigure buttons before the pull | No; the values are secret |
| Draw health, auras, cooldowns | No, beyond its own icon and tooltip | Yes | Yes, by passing secrets to widgets |
| Create, edit, place and bind macros | Not applicable | Yes | No; queued until combat ends |
| Keep data, build interface, validate text | No | Yes | Yes, except changes to protected frames |

The macro owns the action and the add-on owns authoring, placement and display. Neither can make a health-, buff- or cooldown-based choice in combat: macros never had the conditions, and add-ons lost the information. This extends the earlier report's finding on the priest macro. The buff check that a macro cannot make, an add-on cannot make on the player's behalf either; an add-on can show that Inner Fire is missing, and the press remains the player's.

The Forever macro add-ons are the practical proof. At least a dozen target interface 16001, and their documented limits coincide. They read the spellbook and bags, assemble ordinary macro text, store it in the standard macro slots, and optionally place it on a bar or bind a key, all out of combat. None executes an action, none exceeds two hundred and fifty-five characters, and each queues its writes until combat ends. Modified states that "Macros cannot be placed inside a macro" ([Modified](https://www.curseforge.com/wow/addons/modified)); MacroUI that it "generates macros but does not cast spells automatically" ([MacroUI](https://www.curseforge.com/wow/addons/macroui)); GodMacro that "Combat keys cannot choose new recipients or swap consumables mid-fight" and that it "reports unavailable checks rather than inventing values" ([GodMacro](https://www.curseforge.com/wow/addons/godmacro)). That these add-ons call the standard create and edit functions is inferred from their behaviour, which matches the calls in Blizzard's own Forever macro window; their pages do not name the calls. The sequence add-on GSE runs on Forever from version 3.3.38 with the sequence on an action-bar button, and its own key bindings do not work there ([WoW Lazy Macros thread](https://wowlazymacros.com/t/wow-forever-sol-beast-mastery-hunter-level-1-60-gse/64465)).

Blizzard holds this line by engineering more than by rule. Protected functions, lockdown, secret values and hardware-event requirements are enforced in the client, and Blizzard closed side channels during the beta: a leak of minimap rotation during encounters on 8 October 2026, and the server and spawn parts of creature identifiers, obfuscated on 16 October to defeat layer detection ([Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). The stated intent is Midnight's: "Addons should not be able to automate combat decisions for the player" ([Blizzard, combat add-on changes](https://worldofwarcraft.blizzard.com/en-us/news/24244638/how-midnights-upcoming-game-changes-will-impact-combat-addons)). Account action is reserved for what happens outside the client; Blizzard's input-broadcasting policy makes software that mirrors keystrokes to several clients an actionable offence ([Blizzard, input broadcasting policy](https://worldofwarcraft.blizzard.com/en-us/news/23558957/policy-update-for-input-broadcasting-software)). The rule "one key press, one action" is a community paraphrase, not official text, and no Forever-specific statement from Blizzard on macros, key-press multiplication or sequence add-ons was found.

## Conclusion

The macro-condition vocabulary is the single decision language of the Forever client in combat. Macros speak it directly; add-ons reach it through state drivers; nothing else may decide. Any wish for a new in-combat decision, by macro or by add-on, therefore reduces to a wish for a new condition in the engine's parser, which Blizzard's stated design goal opposes. The design space that remains is presentation: an add-on's value on Forever lies in what it draws through the engine's widgets and in what it prepares before the pull.

The rules will move with retail. Blizzard said to expect similar interface changes in both game types ([Warcraft Wiki, 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)), and its game director named interrupt trackers on 14 September 2026 as a target for further restriction ([Warcraft Tavern interview](https://www.warcrafttavern.com/forever/news/ion-holly-interview-blizzcon-2026/)). Techniques that recover hidden combat values by a side route have a short life, as the beta fixes show. The split in the evidence is itself durable: the Lua half of every rule can be re-read from the Forever branch at each build, while the engine half can be established only by test in the client, and at eight days past launch most of those tests have not been published. The next patch will also change the interface number and flag every Forever add-on out of date until its manifest is revised.
